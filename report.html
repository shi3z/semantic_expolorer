What stream batch actually buys

SD 1.5 + LCM-LoRA · 4 denoising steps · 512×512 · frame buffer 1

SD-Turbo never exercises StreamDiffusion’s core trick — the wrapper routes turbo models through a single batched UNet call and skips the pipeline buffer entirely. To measure the algorithm you need a model that genuinely needs several steps.

Sequential denoising

3.32img/s

301 ms per image — four batch-1 UNet calls, one after another

Stream batch

4.40img/s

227 ms per image — one batch-4 UNet call, four images in flight

1.33× faster, for 0.1 GiB more VRAM

That is the whole idea of the paper. Rather than running four sequential UNet calls at batch 1 to finish one image, keep four different images in flight — each at a different point in the denoising schedule — and denoise all four in a single batch-4 call. Every call retires one finished image and admits one fresh noise sample.

The arithmetic is identical; only the shape of the work changes. One large kernel launch instead of four small ones is exactly what an under-occupied GPU wants. The size of the win is bounded by how latency-bound the batch-1 case was to begin with — 1.33× here, and larger on a card with more idle SMs.

Batching is the lever. Frame buffer 1 → 8 buys 36% at 512×512; past 8 it is flat (15.43 → 15.51), so 8 is the knee on this card. At batch 1 the GPU is latency-bound; by batch 8 it is compute-bound.

Resolution scales almost exactly linearly. 384×384 runs 1.70× faster than 512×512 for 1.78× fewer pixels — confirming the UNet, not memory traffic, is the bottleneck at these batch sizes.

PIL conversion costs about 10% (17.12 → 15.43 img/s). That is CPU-side tensor→uint8→PIL work, not generation. Feeding a display surface or a video encoder directly, keep output_type="pt".

LCM-LoRA needs its four steps. At one step it runs at 10.8 img/s and produces an unusable smear. SD-Turbo is distilled for single-step sampling and is sharp there — which is why it wins outright on this card.

Getting it to build

Upstream pins diffusers 0.24 from November 2023, which no longer imports

Rather than pinning the whole stack backwards, the package is installed with --no-deps onto a current diffusers and three API drifts are patched at import time.

fuse_lora

Keyword arguments were replaced

diffusers dropped fuse_unet= and fuse_text_encoder= for components=[…]. Required for the LCM-LoRA path; without it nothing multi-step loads.

from_pretrained

Downloading far more than needed

Upstream calls it with no arguments at all, which drags in the 1.2 GB safety checker and fp32 weights. The shim forces safety_checker=None, fp16, and prefers the fp16 weight variant.

retrieve_latents

Moved out of the img2img module

Restored onto the module upstream imports it from, if absent. Still present in 0.40, so this one is currently a no-op — it is insurance, not a fix.

TensorRT

Left on the table

Upstream’s headline numbers come from TensorRT, which needs polygraphy, onnx and cuda-python at 2023 versions. torch.compile is also out — no Triton and no MSVC 2022 on this box. Both remain the largest available wins.

Reproduce

From a clean checkout

# environment
uv venv --python 3.11 .venv
uv pip install --index-url https://download.pytorch.org/whl/cu128 torch torchvision
uv pip install diffusers transformers accelerate safetensors peft fire omegaconf pillow
uv pip install --no-deps -e ./upstream

# the grid above
python demo.py --model stabilityai/sd-turbo --t-index 0 --count 12 --cols 4

# peak throughput
python bench.py --model stabilityai/sd-turbo --t-index 0 --fbs 8 \
    --width 384 --height 384 --iters 30

# the stream-batch ablation
python bench.py --model stable-diffusion-v1-5/stable-diffusion-v1-5 \
    --t-index 0,16,32,45 --lcm-lora --iters 30
python bench.py --model stable-diffusion-v1-5/stable-diffusion-v1-5 \
    --t-index 0,16,32,45 --lcm-lora --no-denoising-batch --iters 30
